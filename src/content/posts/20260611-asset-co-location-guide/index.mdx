### Introduction

Palo supports a **content co-location / asset co-location** workflow: keep each post or project in its own folder, place images right next to the markdown file, and let the build pipeline optimize them automatically.

This guide explains when to use co-located assets versus `public/`, how to write image paths, and which components already support both sources.

Palo 支持**内容混用 / 资产共存**工作流：每篇文章或项目放在独立文件夹中，图片与 Markdown 文件放在一起，构建时由 Astro 自动优化。

本指南说明何时使用共存资产、何时使用 `public/`，如何书写图片路径，以及哪些组件已支持双来源。


### Why Co-location?

#### Keep related files together

Instead of scattering images across `public/posts/` and hunting for the right filename, everything for one article lives in one place:

```
src/content/posts/20260611-asset-co-location-guide/
├── index.mdx
├── cover.jpg
├── breakout-full.jpg
└── diagram.png
```

#### Smaller images, faster pages

Images under `src/` are processed by Astro's built-in Image component at build time. Palo resolves co-located paths to `ImageMetadata`, then outputs formats like WebP at the display size you need — not the full original file.

Typical benefits:
- Cover images on list cards are resized to card dimensions (e.g. 800×500)
- Post headers use a larger but still optimized variant (e.g. 1600×900)
- Less bandwidth for readers, especially on mobile

#### When `public/` is still the right choice

Use `public/` when you need the **original, unprocessed file** served as-is — for example:
- Screenshots or diagrams that must stay pixel-perfect at full resolution
- Assets referenced by external tools or hard-coded URLs
- Legacy content you do not want to move yet

Palo still supports `public/` everywhere. Co-location is recommended for **new** content, not a forced migration.


### Supported Image Sources

Palo accepts images from three locations:

| Source | Path example | Build behavior |
|--------|--------------|----------------|
| **Co-located** | `./cover.jpg` | Astro Image optimization |
| **src/assets** | `@assets/images/foo.jpg` | Astro Image optimization |
| **public** | `/posts/docs/hero.png` | Served as static file (original size) |


### How to Reference Images

#### 1. Frontmatter cover image (co-located)

Place `cover.jpg` beside `index.mdx` and reference it with a relative path:

```yaml
title: Asset Co-location Guide
coverImage: ./cover.jpg
coverImagePosition: head
```

Wrap the fields above between YAML frontmatter delimiters (three dashes) at the top of your file.

The cover is automatically optimized on the post page, blog list, and homepage LatestPosts.

#### 2. Frontmatter cover image (src/assets)

```yaml
coverImage: @assets/images/projects/project-image-1.jpg
```

Equivalent forms also work: `assets/images/...`, `src/assets/images/...`, `/src/assets/images/...`.

#### 3. Frontmatter cover image (public)

```yaml
coverImage: /posts/docs/cover01.jpg
```

No Astro resizing — the browser loads the file from `public/` at its original dimensions.

#### 4. Images inside MDX body (co-located)

Import the file, then pass the imported value to a component:

```mdx
import diagram from './diagram.png'

<BreakoutImage src={diagram} alt="Architecture diagram" layout="contained" />
```

#### 5. Images inside MDX body (public)

Pass a public URL string directly — useful when you need the original file:

```mdx
<BreakoutImage
  src="/posts/post-image-1.jpg"
  alt="Full-resolution reference screenshot"
  layout="wide"
/>
```

#### 6. Background images (Hero, PaloPageHeader, CreativeSection)

These components use CSS `background-image`. They support `public/` paths and `@assets/...`, but not co-located `./` paths (no content folder context in a page-level prop):

```astro
<PaloPageHeader
  title="Blog"
  backgroundImage="/branding/hero-bg.png"
/>

<Hero backgroundImage="@assets/images/hero-bg.png" />
```

### Recommended Workflow

1. **New posts and projects** — create a folder under `src/content/posts/` or `src/content/projects/` with `index.mdx` and local images.
2. **Cover image** — use `./cover.jpg` in frontmatter.
3. **Inline images in MDX** — `import` co-located files and pass to `BreakoutImage` or other components.
4. **Shared site assets** — keep reusable images in `src/assets/` and reference with `@assets/...`.
5. **Full-resolution originals** — keep in `public/` and use `/posts/...` or `/projects/...` paths when pixel-perfect size matters.


### Summary

Co-location keeps content maintainable and delivers smaller, faster images through Astro's build pipeline. `public/` remains available when you need untouched originals. Palo routes each path to the right renderer automatically — you only need to pick the source that fits your use case.

资产共存让内容更易维护，并通过 Astro 构建管线输出更小、加载更快的图片。当需要原始尺寸时，`public/` 依然可用。Palo 会根据路径自动选择渲染方式——你只需按场景选择图片来源即可。
