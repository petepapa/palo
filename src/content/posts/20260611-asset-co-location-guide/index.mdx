### Introduction

Palo adopts **asset co-location** as the default content management pattern: every post or project lives in its own folder, and its images stay right beside the markdown file — not scattered across a global `public/` or `assets/` directory. This guide gives you the essential rules, the recommended workflow, and the one boundary you must never cross.

Palo 全线推行 **资源同域混用模式（Asset Co-location）** 作为默认内容管理范式：每篇文章或项目独立成文件夹，图片与 Markdown 文件放在一起，不再散落在全局 `public/` 或 `assets/` 目录中。本指南提供核心规则、推荐工作流，以及一条不可逾越的红线。

---

### Why Co-location?

#### Everything in One Place

When images live next to the markdown file that uses them, a post becomes a self-contained unit. You can move it, archive it, or hand it off to another author without hunting down assets scattered across the project tree. One folder equals one complete piece of content.

图片与引用它的 Markdown 文件处于同一目录时，整篇文章就成为一个自包含单元。你可以移动它、归档它，或者交给其他作者，而不需要在项目树中四处寻找散落的资源文件。一个文件夹就是一篇完整的内容。

#### Automatic Optimization

Images placed under `src/content/` are processed by Astro's build pipeline. Palo resolves co-located relative paths (e.g. `./cover.jpg`) into optimized `ImageMetadata`, then outputs WebP/AVIF formats at the exact display dimensions — not the full original file. The result is smaller page payloads and zero layout shift, with no manual configuration.

放在 `src/content/` 下的图片会经过 Astro 构建管线处理。Palo 将同域相对路径（如 `./cover.jpg`）解析为优化后的 `ImageMetadata`，然后按实际显示尺寸输出 WebP/AVIF 格式——而不是原始文件大小。结果就是更小的页面体积和零布局偏移，无需任何手动配置。

#### The Intuition: `./` Just Works

The simplest rule in Palo: if an image belongs to a post, reference it with `./filename.jpg`. No aliases, no build configuration, no global path hunting. It works exactly how you expect local file paths to work — because that's what they are.

Palo 中最简单的规则：图片属于文章，就用 `./文件名.jpg` 引用它。没有别名、没有构建配置、不需要在全局路径中寻找。它完全按照你对本地文件路径的直觉工作——因为它们就是本地文件路径。

### Recommended Directory Structure

When a post needs multiple local images, convert it to an `index.mdx` inside its own folder. Place a `cover.jpg` at the root and organize supporting media in an `assets/` subdirectory.

当一篇文章需要引用多张本地图片时，将文章转换为独立文件夹内的 `index.mdx`。封面图 `cover.jpg` 放在根目录，辅助媒体归类到 `assets/` 子目录：

```text
src/content/posts/
└── 20260611-my-awesome-post/
    ├── index.mdx             <--- your article / 文章正文
    ├── cover.jpg            <--- cover image / 封面图
    └── assets/              <--- post-specific media / 本文独享媒体
        ├── step-01.png
        └── demo.gif
```

This is the canonical layout for every new post in Palo. It keeps the article portable and the asset relationship obvious.

这是 Palo 中每篇新文章的标准目录布局。它让文章可移植，也让资源归属关系一目了然。

### How to Reference Co-located Images

#### Cover Image in Frontmatter

Place `cover.jpg` next to `index.mdx` and reference it with a relative path. Palo automatically optimizes it for the post page, blog list cards, and the homepage LatestPosts section.

将 `cover.jpg` 放在 `index.mdx` 同目录并在 frontmatter 中引用。Palo 会自动为文章页、博客列表卡片和首页 LatestPosts 区域进行优化：

```yaml
coverImage: ./cover.jpg
coverImagePosition: head
```

---

#### Inline Images with Markdown Syntax

Standard Markdown image syntax works directly with co-located paths. The image is resolved at build time and routed through Astro's optimization pipeline.

标准 Markdown 图片语法直接支持同域路径，图片在构建时解析并送入 Astro 优化管线：

```markdown
![封面图](./cover.jpg)
![架构图](./assets/diagram.png)
```

No imports, no components — just standard Markdown. This is the recommended approach for straightforward inline images.

无需 import、无需组件——纯 Markdown 即可。这是简单内嵌图片的推荐方式。

---

#### Inline Images with BreakoutImage Component

For images that need dramatic visual presence — hero shots, section dividers, full-width showcases — use Palo's `BreakoutImage` component. Import it once at the top of your MDX file, then reuse it with direct relative paths for every co-located image on the page.

对于需要强烈视觉冲击力的图片——主视觉、章节分隔、全宽展示——使用 Palo 的 `BreakoutImage` 组件。在 MDX 文件顶部导入一次，之后页面中所有同域图片直接写相对路径即可：

```mdx
import BreakoutImage from '@components/BreakoutImage.astro'

<!-- co-located image — write the relative path directly / 同目录图片直接写相对路径 -->
<BreakoutImage
  src="./cover.jpg"
  alt="Product hero shot"
  layout="full"
/>

<!-- another co-located image — same component, different layout -->
<BreakoutImage
  src="./assets/diagram.png"
  alt="Architecture overview"
  layout="wide"
/>
```

The component internally resolves co-located paths through `import.meta.glob`, feeding them into Astro's Sharp engine for WebP compression, responsive `srcset`, and CLS-free sizing. Three layout modes are available: `full` (edge-to-edge), `wide` (small edge gaps, rounded corners), and `contained` (within article width).

组件内部通过 `import.meta.glob` 自动解析同域路径，送入 Astro 的 Sharp 引擎进行 WebP 压缩、响应式 `srcset` 和零 CLS 尺寸处理。提供三种布局模式：`full`（边缘到屏幕边缘）、`wide`（保留小间隙、圆角）和 `contained`（保持在文章宽度内）。

### The `<img>` Tag Boundary

**This is a hard rule. Do not cross it.**

**这是一条刚性红线，不可逾越。**

Native HTML `<img>` tags cannot reference co-located relative paths. Astro's build-time optimization only activates through component or Markdown-syntax references — raw HTML bypasses the entire pipeline. Attempting `./cover.jpg` inside an `<img>` tag will fail at build time with a `LocalImageUsedWrongly` error.

原生 HTML `<img>` 标签不能引用同域相对路径。Astro 的构建时优化仅通过组件或 Markdown 语法引用激活——原始 HTML 会绕过整个管线。在 `<img>` 标签中使用 `./cover.jpg` 会在构建时报 `LocalImageUsedWrongly` 错误。

```mdx
<!-- ❌ Wrong / 错误 — co-located path in raw HTML -->
<img src="./cover.jpg" alt="封面" />

<!-- ✅ Correct / 正确 — public/ path in raw HTML -->
<img src="/posts/20260611-my-post/cover.jpg" alt="封面" />
```

If you must use an `<img>` tag, the `src` must point to a file inside the `public/` directory. There is no workaround — this is how Astro's static build architecture works.

如果你必须使用 `<img>` 标签，`src` 必须指向 `public/` 目录中的文件。没有变通方案——这是 Astro 静态构建架构的底层约束。

---

### When `public/` Still Matters

`public/` is not deprecated — it is repositioned as a **static asset reserve** for specific edge cases. Use `public/` when:

- You need the original, unprocessed file served as-is (e.g. high-resolution downloads)
- An external system or hard-coded URL references the asset directly
- The image is a one-off that doesn't warrant its own folder structure

`public/` 并未被废弃，而是被重新定位为特定场景下的**静态资源保留区**。以下情况仍应使用 `public/`：

- 需要保留原始未压缩文件（如供用户下载的高清原图）
- 被外部系统或硬编码 URL 直接引用
- 不值得建立独立文件夹的一次性图片

For everyday post images and covers, co-location is the default. `public/` is the fallback, not the starting point.

日常文章的配图与封面，一律使用同域混用模式。`public/` 是备选方案，不是默认起点。

### Quick Reference

| Scenario | Syntax | Image Location |
|----------|--------|---------------|
| Cover (frontmatter) | `coverImage: ./cover.jpg` | Same folder as `index.mdx` |
| Inline (Markdown) | `![alt](./assets/demo.png)` | Same folder or subdirectory |
| Inline (BreakoutImage) | `<BreakoutImage src="./hero.jpg" />` | Same folder or subdirectory |

| 场景 | 写法 | 资源位置 |

| 站点共享资源 | `@assets/images/logo.svg` | `src/assets/` |

### Summary

Asset co-location is the recommended default for all new content in Palo. Place your Markdown and images in the same folder, reference them with intuitive `./` relative paths, and let the build pipeline handle optimization. The one rule to remember: raw `<img>` tags require `public/` paths — everything else flows through co-location.

资源同域混用是 Palo 中所有新内容的推荐默认模式。将 Markdown 与图片放在同一目录，用直觉化的 `./` 相对路径引用，剩下的优化交给构建管线。唯一需要记住的规则：原生 `<img>` 标签必须使用 `public/` 路径——其余一切走同域混用。

> **The intuition to carry**: if an image belongs to a post, don't let it leave the post's folder.
>
> **一条直觉**：图片属于文章，就不要让它离开文章的文件夹。
